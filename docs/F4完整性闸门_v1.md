## 一、本期 F4 的范围（建议批准，附三条边界）

| 本期**做** | 本期**不做**（不得宣称） |
|---|---|
| 热点行的**逐行时间占比** | **逐行内存归因**（"这行占多少内存"） |
| 热点行**周边代码**（±N 行 + 所在函数/循环链） | 完整调用链（跨函数/跨文件深度） |
| **程序级**空间信息（`peak_tracemalloc_mb` / `peak_rss_mb`） | 规模变量（n、数据规模随行的变化） |

三条边界（写进提示词与文档，避免答辩被问穿）：

1. **逐行时间是插桩后的**：只能给「占已剖析行时间之和的百分比」，不得写成「占总运行时间」，
   `case_ms < 2 ms` 时**只给执行次数**（不给占比，分母本身是噪声）。
2. **程序级峰值 ≠ 逐行归因**：反馈里必须写「程序级」三个字；不得出现「这一行耗了 X MB」这类表述。
3. **空间信息在原生题上多半没信号**：实测 EffiBench 原生题 `peak_rss` 可分辨 **0/19**、
   `peak_tracemalloc` 中位 0.0017 MB。所以 F4 必须允许把空间字段写成
   `n/a（本题空间不可分辨）`，**不许为了凑满反馈而填数字**。

## 二、闸门五项（全过才允许写 `ours`）

| # | 检查项 | 通过判据 | 不通过时 |
|---|---|---|---|
| **G1** | 反馈完整性标记 | `diagnostics` 里四个键都在：`hotspot_mode`、`case_ms`、`profiler_overhead_ratio`、`space_status`。**`profiler_overhead_ratio` 允许走「不适用通道」**（见 §六-①）：值为 `null` 时必须在 `diagnostics.not_applicable.profiler_overhead_ratio` 写明 `case_too_small`，且实测 `case_ms < 2.0` | 不写 Result，`degrade_reason` 按目标档位填，`can_write_result=False` |
| **G2** | 占比口径 | **插桩类数字**不得以绝对毫秒出现：逐行部分只能是「占已剖析行时间之和的百分比」（并注明分母）。**harness 测的最慢用例耗时不受限**（见 §六-②），必须保留。`case_ms < 2` 时逐行部分**既无毫秒也无百分比** | 同 G1 |
| **G3** | 空间字段诚实 | 空间值来自 `Result.mem`（程序级），且当 `space_status != "measured"` 时写 `n/a（空间不可分辨）` | 同 G1 |
| **G4** | 诊断不改状态 | 行级诊断失败（`timeout`/`code_error`/`missing_dependency`/`line_mismatch`）只出现在 `diagnostics`，**`Result.status` 与 harness 一致** | 同 G1（必须修代码） |
| **G5** | 与 F3 可区分 | 同一题、同一份代码，F4 的提示词与 F3 的提示词**不同**（`hotspot_mode` 不同 或 反馈含周边代码），并有离线对照留档 | 视为「F4 退化成 F3」，不写 `ours` |
| **G6** | 正式题目 | `formal_task=True`（题目来自冻结题库）。构造的诊断用例即使 G1–G5 全过，`suggested_method` 也只能是 `diagnostic` | 写 `ours` → 拦（`G6`） |

**只有 G1–G6 全过，且该题 `can_write_result` 为真，才允许把 `method` 写 `ours`。**
任何一项不过 → 写实际生效档位（`f3`/`f2`/`f1`）+ `degrade_reason`，**不要**用 `ours` 占位。

## 六、两处边界裁定（2026-11-28，回应 C）

### ① `case_ms < 2` 时 `profiler_overhead_ratio` 记「不适用」，**允许通过 G1**，但该题不得写 `ours`

**为什么不是「必须降级到失败」**：不跑逐行计时是**按约定不该跑**，不是「跑坏了」。
把「按设计不适用」判成失败，会让所有小题的 `%Correct` 分母凭空变差。

规则（三条同时满足才算合法不适用）：

| 条件 | 说明 |
|---|---|
| C1 | `case_ms` **有实测值**且 `< 2.0`（这就是依据；不许拿 `null` 顶替） |
| C2 | `diagnostics.not_applicable.profiler_overhead_ratio = "case_too_small"`（显式写原因，不是留空） |
| C3 | 该记录 `effective = "f3"`、`degrade_reason = "no_hotspot"`、`method` 写 `f3`，**不写 `ours`** |

也就是说：**闸门放行这一条记录，但不放行「它是 Ours」这个说法。**
判「不适用」和判「失败」是两件事——前者进 `not_applicable`，后者进 `error`。

### ② G2 只禁**插桩数字**的绝对毫秒；F2 共用的「最慢用例耗时」必须保留

| 数字 | 来源 | 允许绝对毫秒？ | 理由 |
|---|---|---|---|
| 最慢用例耗时 `case_ms` | `harness.measure_cases()` | ✅ 必须保留 | 同一把尺子测的官方值，是模型理解「这题多慢」的唯一锚点 |
| 逐行时间 | `line_profiler`（插桩） | ❌ 只能百分比 | 插桩开销 2.8–6×，绝对值没有物理意义 |
| 逐行执行次数 | `sys.settrace` 计数 | ✅（次数无单位歧义） | F3 的原生形式 |

**机器可检的定义**（Codex 直接照这个写）：

```
diagnostics.line_timing.numbers_in ∈ {"percent", "hits_only"}
若 numbers_in == "percent": feedback 的【逐行区块】里不得出现 /\d+(\.\d+)?\s*ms/
                             且必须含「占已剖析行时间之和」
若 numbers_in == "hits_only": 逐行区块里不得出现任何毫秒或百分比
无论哪种：feedback 的【最慢用例区块】允许且应当出现 "Case execution time: X ms"
```

**分区呈现**（避免歧义）：反馈里两块分开，各自带来源标签——

```
Slowest test case (measured by harness, not instrumented):
  <src>
  Case execution time: 12.3450 ms.

Hot lines (占已剖析行时间之和；line_profiler 插桩值，不可与运行耗时比较):
  L42: 31.2% | 118 hits | ...
```

### ③ 附：`diagnostics` 最小契约（闸门直接照抄）

```json
{
  "hotspot_mode": "line_profiler | line_hits | none",
  "case_ms": 12.345,
  "profiler_overhead_ratio": 2.83,
  "space_status": "measured | below_floor | unmeasured",
  "not_applicable": {"profiler_overhead_ratio": "case_too_small"},
  "line_timing": {"numbers_in": "percent", "denominator": "profiled_lines_sum"}
}
```
`not_applicable` 允许为空对象 `{}`；但只要某个键缺失又没写进 `not_applicable`，**G1 不通过**。
