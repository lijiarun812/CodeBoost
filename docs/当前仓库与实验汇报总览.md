# CodeBoost 当前仓库与实验汇报总览

> 整理日期：2026-11-28。依据当前工作树中的代码、原始结果和阶段报告。本文是汇报索引，不把不同数据集、模型和测量口径的数字合并统计。

## 一、项目定位与可讲的研究问题

项目研究**在保持代码正确性的前提下，执行反馈能否帮助大模型生成更快的代码**。方法来源有两条：PerfCodeGen 的「失败测试修正确性、最慢测试反馈优化时间」，以及 EffiLearner 的「执行开销与剖析反馈驱动迭代」。EffiBench 提供效率题目和测试。当前重点已由笼统证明“增强反馈更好”，收敛为三个可检验的问题：

1. 给执行反馈是否优于只要求优化？
2. 反馈从总耗时、最慢测试到行级热点逐步细化，收益是否递增？
3. 细化反馈的收益是否抵得上采集时间、提示 Token 和调用延迟？

## 三、两篇前置论文的复现：已经做到哪里

### 3.1 EffiLearner

轻量版实现了「生成初始解 → 测量开销 → 把开销反馈给模型 → 多轮优化 → 按判据保留候选」。仓库记录了 4 个模型、各 100 题、3 轮的运行：成功执行分别为 87、80、82、79 题，旧汇总的时间下降分别为 27.5%、23.9%、18.3%、15.6%（模型顺序见 [`README.md`](../README.md)）。这证明简化管线可以跑通，**不能作为反馈相对无反馈的因果效果**，因为该组没有严格无反馈对照。

论文完整方案包含行级时间和内存剖析；这批轻量复现主要提供汇总开销数字，不能称为完整复现其全部反馈档位。更重要的是，旧 `mem_mbs` 是 RSS 随时间的积分，时间变短本身会使它下降；在 328 条可重算记录中有 101 条零积分。归一化并排除零积分后，仓库报告的可测口径下降约 9.3%（227 条），但它仍不等于可靠的峰值空间收益。见 [`表格_复现口径对比.md`](表格_复现口径对比.md) 和 [`主线首跑报告.md`](主线首跑报告.md)。后者另记录 20 题真实模型运行 19 题完成，以及剖析开关不对称、思考模式配置造成的执行问题；这批结果与前述 4 模型矩阵是**不同批次**。

### 3.2 PerfCodeGen

[`perfcodegen/pcg_repro.py`](../perfcodegen/pcg_repro.py) 实现 base → 失败测试纠正 → 最慢测试性能优化三相流程，复用仓库内的官方提示模板和清洗代码，可离线 mock 自检，也可接真实 API。它是**单机轻量复现**：执行层、题目切分、重复计时及采样数与论文设置不同；默认单采样不能解释为论文的 Best@5/10。仓库已有 deepseek-flash 的少量逐题记录，现有论文对照表中的 PerfCodeGen 实跑仅 1 题，适合演示流程，**不足以声称复现论文的总体性能结论**。详见 [`perfcodegen/README.md`](../perfcodegen/README.md) 与 [`表格_论文vs复现.md`](表格_论文vs复现.md)。

两套轻量复现和下述 G0～G3 实验使用不同模型、题集、采样和评测口径；汇报时把它们作为“方法来源与工程基础”，不要把数字拼成一张方法优劣总榜。

## 四、原实验的验证与结论

### 4.1 12 题 HumanEval 预实验

原始 Base、Vanilla、PerfCodeGen、Ours 对照验证了提示词和测试管线，但不少基线为亚毫秒级，部分初始代码错误或优化后失正确。它说明**计时噪声、题目太简单和正确性检查**会直接影响结论，不能据此断言“热点反馈优于最慢测试反馈”。记录见 [`experiment/results/report.md`](../experiment/results/report.md) 与 [`结果解读与冲分方案.md`](结果解读与冲分方案.md)。

### 4.2 EffiBench 首轮与额外测试

首轮冻结 30 题，22 题完成三组性能比较；原测试集的初始代码耗时中位数仅约 0.581 ms。三组复测正确为 Vanilla 16/22、PerfCodeGen 18/22、增强反馈 19/22，不能据此宣布某组稳定领先。对 22 题另用固定随机种子生成额外断言，基准解与初始代码全部通过；三个优化组分别有 15、18、19 题通过。最醒目的失败案例是 **809**：PerfCodeGen 候选在原测试约快 93.67 倍，但在新构造的 2,100 个单词输入上反而约慢 14 倍。它说明固定小测试上的极大加速不能代表大输入性能。见 [`effibench_main_report.md`](../experiment/results/effibench_main_report.md)、[`stage1_validation.md`](../experiment/results/stage1_validation.md)。

### 4.3 困难题筛选与第二轮探索

对 908 道可解析题按预设规则筛选：初始解和基准解均正确、初始解至少 1 ms 且至少比基准解慢 2.5 倍。22 题入选，额外测试又排除 1 题，最终 21 题完成 Vanilla、PerfCodeGen、热点增强、总耗时反馈四组。主组 15 题中，两套测试都正确的数量分别为 12、10、10、13；热点增强与 PerfCodeGen 都正确的 9 题里，热点增强仅 3 题更快，成对速度比中位数 0.98。不同组“正确候选的中位加速”覆盖的题目集合不同，不宜直接比较。见 [`stage2_screening.md`](../experiment/results/stage2_screening.md) 与 [`effibench_v2_report.md`](../experiment/results/effibench_v2_report.md)。

**原实验给出的研究转向**：先固定同一题、同一初始代码和优化指令，再隔离反馈内容；短任务单列；只在正确候选中比较速度，并报告失败。此前结果保留为探索证据，不与新实验混算。

## 五、新实验：G0～G3 的设计、效果与回答

| 组 | 给模型的执行反馈 | 相比上一组增加 |
|---|---|---|
| G0 | 无 | 统一优化指令 |
| G1 | 固定测试集总耗时 | 程序级时间 |
| G2 | G1 + 最慢测试及其耗时 | 用例级瓶颈 |
| G3 | G2 + 最慢测试中的热点源码行、执行次数、近似行耗时 | 行级热点 |

四组使用同一初始代码、优化指令、qwen4-max、输出上限和每组两次生成；反馈在模型调用前采集并冻结。21 道候选题中 17 道通过计时和热点稳定性预检（12 道主组、5 道短任务对照），合计 136 次调用。成功标准：原测试正确且不变慢，额外测试正确且至少快 1.3 倍。见 [`g_stage1_feedback.md`](../experiment/results/g_stage1_feedback.md) 至 [`g_stage4_findings.md`](../experiment/results/g_stage4_findings.md)。

| 主组指标（12 题、每组 24 次生成） | G0 | G1 | G2 | G3 |
|---|---:|---:|---:|---:|
| 两套测试均正确 | 20/24 | 21/24 | 22/24 | 22/24 |
| 达到成功标准 | 20/24 | 20/24 | 22/24 | 22/24 |
| 正确候选的额外测试中位加速* | 13.90× | 15.00× | 23.94× | 16.03× |
| 提示 Token 中位数 | 646 | 670 | 924 | 1128 |
| API 延迟中位数 | 4.30 s | 4.98 s | 5.34 s | 5.52 s |

\*各列正确候选集合不同；方法比较应看同题成对数据。相邻组在双方正确的题次中，G1/G0、G2/G1、G3/G2 的速度比中位数分别为 **1.02、1.02、0.81**；后组更快次数分别是 10/19、13/21、7/22。5 道短任务在四组均为 10/10 成功，高倍加速更多反映共同的弱初始代码。

**目前能回答**：G1 相比 G0 没有增加成功次数，单独提供总耗时的增益未获支持；G2 比 G1 多 2 次成功，但样本小；G3 没有再增成功次数，成对速度反而更低。G3 还增加提示长度、API 延迟及约 0.105 s 的热点采集成本。数据不支持“反馈越细越好”，但也不能证明细粒度反馈普遍无效。三次计时极差/中位数的中位约为原测试 3.9%、额外测试 4.3%；热点行耗时是跟踪器近似值。完整表与原始数据见 [`g_report.md`](../experiment/results/g_report.md)、[`g_analysis.json`](../experiment/results/g_analysis.json)。

## 六、汇报时必须说明的边界

- **研究对象**：G 轮只研究时间反馈颗粒度；没有可与时间并列的可靠空间指标。EffiLearner 旧 TMU、归一化内存和峰值 MU 要分开讲。
- **外推范围**：主组只有 12 题、每题每组两次生成；额外测试未给模型，但仍由同一基准生成器产生，不是真正跨来源测试。
- **测量与正确性**：超时、初始解失败、候选失正确、反馈不稳定分别记账；错误代码不应获得普通加速比。剖析计时不能与无剖析绝对计时相减。
- **论文关系**：PerfCodeGen 与 EffiLearner 均为轻量复现或借鉴，单机执行、题集、模型和采样量与论文不同；不能直接复称论文的总体结果。
- **潜在偏差**：困难题按初始解慢于基准解的规则筛入，因而 G 轮高绝对加速不能代表随机题上的普遍优化效果。

## 七、下一步实验与执行流程

1. **冻结真正的大输入诊断集**：对现有 12 道主组题逐题构造小、中、大输入和边界用例，先用独立参考实现或可靠判题器验证预期输出；记录生成规则、随机种子、剔除原因。优先复核 809 一类“原测试极快、大输入变慢”的案例。完成后不按实验结果重选题。
2. **先做无 API 的重评测**：用已有 G0～G3 候选在冻结大输入上复核正确性和时间，保持同题同环境的成对重复计时。给每题报告原测试、额外测试和大输入三列；把噪声阈值、超时和失正确独立列出。若表现变化明显，再讨论是否需要新增模型生成。
3. **做失败案例分析**：至少展示近最优无可优化空间、瓶颈误判、优化后失正确、计时噪声和大输入反转各一例。每例列原代码与候选关键差异、反馈内容、正确性和多档时间，说明原因而非只放加速比。
4. **补足统计与成本**：按题聚合成对差异，给出改善/持平/变差的题数及不确定区间；如免费额度允许，再增加独立生成次数或题目数。同步报告反馈采集时间、Token 和 API 延迟，避免只报速度收益。
5. **空间作为独立支线**：参考 [`空间可测性_升档实验.md`](空间可测性_升档实验.md)，只在峰值有可分辨信号且大输入已校验正确性的题上比较空间；其余题明确标记“不可测”，不以 TMU 下降代替空间收益。
6. **形成最终汇报材料**：按“论文方法 → 轻量复现与差异 → 原实验暴露的问题 → G0～G3 设计 → 成对结果与成本 → 失败案例 → 限制与下一步”组织。主图建议为 G0～G3 成功率与成对速度、Token/延迟成本、809 多输入档反转；图表均附样本数与口径。

每阶段结束时记录**预期、实际、是否达标、证据文件和下一步决定**。原始结果与新测量分目录保存，不覆盖既有 JSON。
