## 二、意见 1：第一篇论文的问题怎么处理

不要口头质疑论文，做**论断审计**：每条论断给出「论文说法 → 我们怎么测 → 结果 → 成立条件」。

| 论断 | 审计方法 | 可能的结论形态 |
|---|---|---|
| 执行反馈优于 vanilla | 同预算 k 采样、同 seed，配对 bootstrap 比较 | 只在基线有优化空间时成立 |
| 最慢用例级反馈足够 | F2（论文）vs F3（只给热点行）vs F4（热点区域）消融 | 反馈越靠近代码结构，收益越大 |
| E=12 去极值计时可信 | 输入隔离 + 重复协议敏感性分析（中期 HE/40 已证明会翻转结论） | 论文未交代输入隔离，比值可被假象放大 |
| %Opt 提升即性能提升 | 复核 %Opt 定义，另报 Speedup 与中位数耗时 | %Opt 对阈值敏感，需并列报告 |
| 方法可泛化到 MBPP/APPS | 难度分层后复跑 | 随难度上升收益结构变化 |
| 只优化时间即可 | 加空间维度，看时间-内存是否冲突 | 存在 tradeoff，单目标会牺牲内存 |

交付物：`perfcodegen/claim_audit.md`，每条附一张小表 + 一条能现场展示的案例（HE/40 与 HE/147 就是现成案例）。
结论口径统一为「在什么条件下成立/不成立」，这是本科复现能给的最强结论，也最抗追问。

## 四、意见 3：Ours v2 —— 行级时间 + 空间优化

1. **双口径内存，不混用**
   - `tracemalloc` Python 堆峰值：可归因到行/函数，用于反馈与 `%Opt_mem`；
   - `RSS` 峰值：进程级真实占用，用于报告；两者分列，禁止用 RSS 差值冒充分配量。
2. **行级内存归因**：在函数入口/出口与循环迭代边界做 snapshot 差分，按分配增量排序；不可精确归因时标注为「attributed allocation」，不夸大精度。
3. **联合目标（Pareto 接受规则）**：候选必须通过正确性门禁，然后
   - 时间改善 ≥5% 且内存回退 ≤10% → 接受；
   - 内存改善 ≥10% 且时间回退 ≤10% → 接受；
   - 两者同时改善 → 强接受；
   - 一方大幅改善另一方大幅回退 → 记入 Pareto 存档，不替换当前解。
4. **必做消融**：time-only / mem-only / joint 三组，证明「同时优化空间」不是口号，也给出冲突案例。
5. **指标**：`%Opt_time`、`%Opt_mem`、`Speedup`、`mem_ratio`、Pareto 覆盖率，以及「时间改善但内存变差」的题数。

## 五、意见 4：替换 180s 硬超时

现状：`sandbox.py` 里 `time_code(..., timeout=180)`、`check_correctness(..., timeout=30)`，一超时就整题判失败。

替代方案（`eval/harness.py`）：

1. **分层预算**：正确性阶段独立预算；计时阶段按输入阶梯逐档给预算，单档预算 = `max(5s, 20 × 该档标定耗时)`，不设全局一刀切。
2. **心跳看门狗**：子进程每完成一档 / 每 N 次循环写一行进度（stderr 或管道），父进程「连续 30s 无心跳」才 kill。这样能区分「任务大但仍在推进」与「死循环」。
3. **超时降档重试**：某档超时 → 回退到上一档继续测，并把「该题在 n=1e6 未完成，以下基于 n=1e5」写进反馈与结果，属于**规模感知反馈**的一部分。
4. **超时分类**：`status ∈ {ok, incorrect, timeout, resource_exceeded, api_failed}`，timed-out 不参与 speedup 统计，单独报超时率与降档率。
5. **资源上限**：父进程设 RSS 上限（如 2GB）与总时长上限，超限记为 `resource_exceeded` 而非「代码错」。

验收：同一份题库重跑，`timeout` 率大幅下降且没有任何一题因「跑得久」被误判为错误；日志里能看到降档记录。

## 六、意见 5：反馈单元从「行」升级为「区域」

现状：`prompts.ours_prompt` 只有 `line {lineno}: {ms} over {hits} hits`，模型看不到这行在哪个循环里、被谁调用。

`optimize/feedback.py` 构造热点区域，每块包含：

- 热点行本身：命中次数、总耗时、单次成本、占总时间比例；
- **所在作用域**：用 AST 定位最近的 enclosing function / for / while / if，把循环头与边界一起给出；
- **周边代码**：热点行前后各 8 行原样代码（不是行号）；
- **调用链**：谁调用它、它调用了谁，各自 cumulative 占比（cProfile 对齐到同一份行号）；
- **规模变量**：该档输入的 n、容器长度，让模型能判断 O(n²) 还是常数过大；
- **内存维度**：该行/该块的分配占比（配合意见 3）。

预算控制：重叠区域合并、按 cumulative self time 排序、总注入 ≤1200 tokens（约 prompt 的 25%）。

消融（这是意见 5 的实证，也是本项目最可能的创新点）：

| 组 | 反馈内容 |
|---|---|
| F0 | 无反馈（vanilla） |
| F1 | 仅总耗时 |
| F2 | 仅最慢用例耗时（论文等价） |
| F3 | 仅热点行（我们中期做法） |
| F4 | 热点区域 + 调用链 + 规模 + 内存（Ours v2） |

预期：在多函数、嵌套循环、递归题上 F4 > F3 > F2；在单函数简单题上五组趋同——这正好解释了中期「12 题看不出差别」的原因。

## 七、意见 6：数据集与难度分层

| 层 | 数据集 | 作用 |
|---|---|---|
| L1 一致性 | HumanEval（164） | 与中期结果对齐，保证可追溯 |
| L2 中等 | MBPP+（EvalPlus，378） | 更多题型、单测更强 |
| L3 效率关键 | EffiBench（class Solution + 大输入 + 6 指标） | 论文指定的效率基准，已有 100 题历史结果 |
| L4 困难 | APPS（competition 子集）/ CodeContests | 真正的算法难度与大输入 |
| 可选 | BigCodeBench 或 SWE-fficiency 1–2 题 | 真实库调用/仓库级，时间允许再做 |

**难度不是主观标签，是三个可测指标**（`eval/difficulty.py`）：

- `baseline_ms ≥ 20ms`（在冻结输入阶梯上），保证信号/噪声 ≥ 20×，直接消灭中期 15 条「噪声带」；
- `headroom = baseline / reference_optimal ≥ 1.5`，保证有优化空间，消灭「原始代码已接近最优」；
- `cv = 重复测量变异系数 ≤ 10%`，保证可复现。

据此从四层里筛出 **120–200 题冻结题库**（含分层配额与 manifest 哈希），所有方法、所有模型只在这份题库上比较。
输入统一用几何阶梯（1e3 → 1e4 → 1e5 → 1e6，按目标测量时长自动升档），EffiBench 优先用其自带大输入。

## 八、统一实验协议（所有人共用，先冻结再跑）

### 8.1 数据结构

```json
Task = {
  "task_id": "HumanEval/40", "dataset": "humaneval|mbpp+|effibench|apps",
  "entry_point": "...", "prompt": "...", "test": "...",
  "inputs": [{"tier": "t2", "n": 10000, "gen": "seed:20261023", "args_hash": "sha256:..."}],
  "difficulty": {"baseline_ms": 42.1, "headroom": 2.4, "cv": 0.04, "category": "list/loop"}
}

Result = {
  "run_id": "...", "task_id": "...", "method": "base|vanilla|f1|f2|f3|ours",
  "manifest": {"model": "...", "model_version": "...", "temperature": 0.2,
               "seed": 42, "dataset_hash": "sha256:...", "harness_commit": "..."},
  "status": "ok|incorrect|timeout|resource_exceeded|api_failed",
  "time": {"median_ms": 0.0, "iqr": 0.0, "tiers": []},
  "mem": {"peak_tracemalloc_mb": 0.0, "peak_rss_mb": 0.0},
  "speedup": 1.0, "mem_ratio": 1.0, "code": "..."
}
```

### 8.2 测量规范

- 子进程隔离；每次调用前 `deepcopy` 独立输入，复制不计时；
- 每档重复 E=12，去最高/最低各 2 个后取 8 个的均值作为主口径 `mean_trimmed_ms`，中位数只作辅口径，**不参与表格比较**；
- 计时前先标定（自适应重复次数，目标 0.25–1s/批），标定不计入结果；
- 结果必须带 `manifest`，缺 manifest 的 run 不进汇总。

> **复现主线（EffiLearner）双列报告**：忠实复现列用论文口径（`mem_mbs` 内存-时间积分 + 重复执行墙钟 `exec_time` + RSS 峰值），
> 新口径列用 `mean_trimmed_ms` / `peak_tracemalloc_mb` / `peak_rss_mb`。两列并列写进同一张表，**不允许混用或相互换算**。
> 若两列结论不一致（尤其 `mem_mbs` 报「内存降 100%」），按论文判据缺陷记录，作为意见 1 的证据，而不是抹掉。

> E=12 的出处：中期报告方法表把「每用例执行 12 次、去极值取均值」归给论文，但那是二手转述、没有页码。
> 期末统一表述为「**本组测量协议**（对齐论文的多次执行 + 去极值思路）」，页码核实之后再决定是否写成「论文规定」。

### 8.3 统计与噪声

- 每配置 3 个 seed × 3 个采样，报中位数 + IQR；
- 加速比用配对 bootstrap 95% CI，**不再用「1.3x 阈值」当结论**，改为「噪声地板法」：同一代码重复测得的 CV 决定阈值，CI 下界 > 1 才算真实提升；
- 不使用「显著」等统计术语，除非真的做了检验。

### 8.4 只有一把尺子

`eval/harness.py` 是**唯一测量实现**，所有 track（`effilearner` / `perfcodegen` / `optimize`）必须调用它。

| 实现 | 处理 |
|---|---|
| `eval/harness.py` | 唯一尺子，新数字只能由它产出 |
| `eval/measure.py` | **仅诊断**：拆单用例、定位最慢用例源码，供拼反馈用；数字不进报告、不参与接受判定 |
| `effilearner/effi_repro.py` 内置的 psutil 积分计时 + 超时 + 热点 | 归档为**旧尺子**，结果保留但打 `protocol_version=legacy-psutil`，不再用于新实验 |
| 中期实验包 `sandbox.py`（`time.time()` + 180s） | 同上，随实验包迁入 `optimize/` 时删掉测量部分，只留提示与流程 |

**新旧对照**：用新尺子在中期 12 题上抽测，输出「旧口径 / 新口径」两列并解释差异来源。
这样既不丢中期成绩，也不会出现两套数字同框比较。

## 十、已知风险

- **API 成本/限流**：模型矩阵会放大 4–5 倍调用量，先用小样本定参数，再全量；成本台账由组长维护。
- **模型版本漂移**：云端模型会静默更新，必须记录 `model_version` 与调用日期，跨周数据不直接合并。
- **APPS/大输入跑得久**：靠心跳看门狗与降档机制兜住，不允许用硬超时截断。
- **Windows 计时噪声**：固定机器、关闭后台、每档 E=12 去极值；跨机器数字不做直接比较。
- **EffiBench 数据集体积（约 87MB）**：不入库，提供下载脚本 + 哈希校验。
