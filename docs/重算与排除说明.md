# 重算与排除说明（`eval/recompute.py`）

> 执行：队员A · 2026-11-27 · 命令：`python eval/recompute.py --inputs "results/matrix/*/repro_*.json"`
> 产物：四份 `*_patched.json`（**原文件一字未动**）

---

## 一、它做什么

读已存的 `repro_*.json`，用**当前 harness** 重算每条记录的 `new_final`（时间 + 双峰值），
**不调模型、不花 API**，输出 `<原名>_patched.json`，每条记录带一个 `recompute` 块：

| 状态 | 含义 |
|---|---|
| `recomputed` | 用 `final_code` 重测成功，`new_final`/`new_time_reduction_pct`/`new_mem_reduction_pct` 已更新 |
| `retryable: candidate_incorrect` | 候选代码本身过不了测试（canonical 能过）→ 需要模型重跑 |
| `retryable: final_code_missing` | 记录里没存 `final_code`，且这题 canonical 能过 → 需要重跑 |
| `excluded: dataset_defect` | **canonical 也过不了同一个测试块** → 这题测不了，不该再挂 `n/a` |

---

## 二、两个必须先说清的事实

### ① `new_baseline` 无法重算

**模型生成的初始代码从未落盘**（记录里只有 `final_code`）。所以 `new_baseline` 保持原值，
并在 `recompute_meta.new_baseline` 里标 `not_recomputable: baseline_code_not_stored`。

**不要**拿 `canonical_solution` 冒充初始代码——那是另一个量（标准解 vs 模型初稿），
混用会让「优化幅度」凭空变化。要在源头解决，只能让 `effi_repro` 以后把 `baseline_code` 一起存下来
（那是组长的文件，我只提建议不擅自改）。

### ② 250 / 285 的 `n/a` **不是数据集缺陷**（推翻我先前的判断）

我上一轮说 250/285 是「数据集坏题」，依据是 `test_case` 字段——**看错字段了**：

| 字段 | 内容 | 谁在用 |
|---|---|---|
| `test_case` | 100 条 assert，250 里把 `TreeNode` **类**当实例传、285 里嵌了对象 repr | 没人用（EffiBench 的 private/原生集） |
| `small_test_cases` | 4–7 条 assert，**自带 `solution = Solution()`**，用 `build_tree` / `build_tree_from_list` | **effi_repro 用的是这个**（`test_block = problem["small_test_cases"]`） |

而 `build_tree` 这些 helper 只在 `effi_repro.build_program()` 里注入，
`new_metrics()` 直接调 harness 时**没注入** → 250/285 在当年就被记成 `n/a`。

**本脚本把同一份 helper 前导补上后，250/285 测出来是 `ok`**：

```
250 无前导: incorrect NameError: name 'build_tree' is not defined   带前导: ok
285 无前导: incorrect NameError: name 'build_tree_from_list' ...    带前导: ok
```

所以它们是 **`recomputed` 可补算**，不是 `dataset_defect`。

## 三、真正的 `dataset_defect` 是另外四题

判据：**`canonical_solution` 加上 helper 前导，仍然过不了同一份 `small_test_cases`**。

| 题 | 现象 | 结论 |
|---|---|---|
| 254 Factor Combinations | canonical `AssertionError` | `dataset_defect` |
| 267 Palindrome Permutation II | canonical `AssertionError` | `dataset_defect` |
| 306 Additive Number | canonical `AssertionError` | `dataset_defect` |
| 314 Binary Tree Vertical Order | canonical `AssertionError` | `dataset_defect` |
| 270 Closest BST Value | canonical `AssertionError` | `dataset_defect` |
| 312 Burst Balloons | canonical `ok`，但记录没存 `final_code` | `retryable` |
| 269 Alien Dictionary | canonical `ok`，但记录没存 `final_code` | `retryable` |

## 四、四份矩阵文件的重算结果

| 文件 | 记录 | 重算前 n/a | 重算后 n/a | recomputed | retryable | excluded |
|---|---|---|---|---|---|---|
| `deepseek-flash` | 20 | 6 | 6 | 15 | 1 | 4 |
| `deepseek-v4-pro` | 20 | 5 | 5 | 17 | 0 | 3 |
| `glm-4.6` | 20 | 3 | **2** | 18 | 0 | 2 |
| `qwen3-coder-flash` | 20 | 6 | 6 | 16 | 1 | 3 |

**为什么大多数 n/a 没有下降**：这些 `n/a` 对应的记录**根本没有 `final_code`**
（基线生成就失败/被判 `incorrect` 的不写代码），所以重算无从下手——
它们要么是 `dataset_defect`（重跑也没用），要么是 `retryable`（换模型重跑才有意义）。

**唯一真正「填上」的是 glm-4.6 的一条**（3 → 2）。

要让 n/a 继续下降，只有两条路：
1. **排除法**：把 `excluded` 的题从分母里去掉，表格里不再显示 `n/a`（这是文档层的事，组长做）；
2. **重跑法**：`retryable` 的两题（312、269）换模型/换 seed 重跑，会产生新的 `final_code`。

如果希望以后「重算」能连 `new_baseline` 一起补，`effi_repro` 需要在每条记录里多存一个
`baseline_code`（约几 KB/题）。**这个我没动，等你说**——它属于复现线文件。
