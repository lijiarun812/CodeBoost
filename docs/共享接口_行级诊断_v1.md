## 1. 你必须消费的两个共享件

### 1.1 前导代码：`eval.harness.PREAMBLE`（新暴露，必修）

**为什么必修**：EffiBench 前 120 题里有 **89 题（74%）** 的 `canonical_solution` 依赖
`from typing import *` 这类前导，而代码里**没有 import**。实测 `problem_idx=4`：

```
不带前导: exec → NameError: name 'List' is not defined
带前导  : exec → ok
```

你的子进程现在是 `namespace = {...}; exec(compile(code, ...))`，**74% 的题会 `code_error`**，
然后静默退化到 hits —— 而你在本机测不出来（你的样例是人写的短函数）。

**接口级写法**（关键是「前导单独编译」，不能拼接，否则行号整体错位）：

```python
_g = {"__name__": "__codeboost_line_timing__"}
if prelude:
    _pre = {"__name__": "__codeboost_prelude__"}
    exec(compile(prelude, "<prelude>", "exec"), _pre)
    _g.update(_pre)
exec(compile(code, SOURCE_NAME, "exec"), _g)   # 仍然从第 1 行开始，行号不变
```

`profile_case(code, case_src, entry_point, *, prelude="", ...)`；
调用方传 `prelude=harness.PREAMBLE`。`eval/hotlines.py` 已按这个写法改好，可直接抄。

### 1.2 逐用例诊断：`harness.measure_cases()` 的返回结构（字段契约）

| 字段 | 含义 / 取值 |
|---|---|
| `status` | **五类权威状态**：`ok` / `incorrect` / `timeout` / `resource_exceeded` / `api_failed` |
| `mode` | 拆分方式：`block_split`（EffiBench 顶层 assert 已拆分）/ `block`（整块一条）/ `humaneval` |
| `cases` | `[{idx, ms, src}]`，逐条用例 |
| `total_ms` | 各条之和（**不是**整块计时，不能当 Result.time） |
| `slowest` | `{idx, ms, src}`，最慢那一条 |
| `reps` | 每条用例的重复次数 |

⚠️ 两处变更你会碰到：
- **不再返回 `cases_ms`**，统一用 `cases[].ms`；
- `mode` 现在可能是 `block_split`。别写 `if mode == "block": ...` 这种假设。

实测（EffiBench `idx=3`，修复后）：`100` 条用例、`total_ms=0.0752`、
`slowest = 0.0016 ms` 且 src 是**一条具体 assert**。

## 2. 状态词表与映射（F5，2026-11-27 修订）

### 2.1 以 `eval/schema.md` 为准：`fallback_f2` **是**合法值

我先前的说法错了。`schema.md:94` 的实际枚举是：

```
null / budget_exceeded（token 预算不足）/ no_hotspot（拿不到行级数据）
/ unsupported_kind（题型不支持）/ fallback_f2（反馈降为最慢用例）
```

**裁定：schema 为准，你保留 `fallback_f2` 是对的。**（C 提出的这条纠正成立。）

### 2.2 `degrade_reason` 描述「**为什么落到当前这一档**」，按目标档位选词

| 最终落到 | `degrade_reason` |
|---|---|
| `f2`（最慢用例） | `fallback_f2` |
| `f1`（只有总耗时） | `no_hotspot` |
| `f3` 但上下文被长度截断 | `budget_exceeded` |
| 题型根本不支持 | `unsupported_kind` |
| 没有降级 | `null` |

也就是说：**`fallback_f2` 与 `no_hotspot` 不冲突**——前者说「降到了 f2」，后者说「连行级数据都没有、只能给总耗时」。
你现在 f3/f4 → f2 用 `fallback_f2`，**正确，不用改**。

### 2.3 诊断自己的状态只进 `diagnostics`，**不进** `degrade_reason`

| 你的 status | 写进哪里 |
|---|---|
| `ok` | `diagnostics.line_timing.status = "ok"` |
| `missing_dependency` / `line_mismatch` / `bad_payload` / `process_error` / `timeout` / `code_error` | `diagnostics.reasons`（人类可读）+ `diagnostics.line_timing.status` |

`degrade_reason` 只按 §2.2 由**目标档位**决定，不由诊断状态直接映射。

### 2.4 正式 `status` 只由 harness 判定（裁定见 §3.3）

**诊断失败绝不改 `Result.status`。** 我先前写的「`code_error → incorrect`」是错的，已删除：
诊断子进程会**重跑一次代码**，它失败的原因可能是探针环境（前导缺失、依赖缺失、超时），
不是被测代码错。让它改判等于把**测量工具的缺陷算到模型头上**。

## 3. 门槛、超时与提示词格式（F3 / F4，2026-11-27 修订）

| 项 | 约定 |
|---|---|
| 超时 | `timeout_s = max(10.0, 20 * slow_ms / 1000)`；把 `slow_ms` 与 `timeout_s` 都写进 `diagnostics`，事后能判断阈值紧不紧 |
| 小用例门槛 | `case_ms < 2.0` → 直接降级，**既不给毫秒也不给占比**（分母本身就是噪声），只给 `hits` |
| 提示词格式 | **占比为主、绝对值为辅**（见 §3.2） |
| 分位 | 每次只喂 top-3，带行号与源码原文（你已做） |

### 3.1 诊断超时不必接 harness 心跳（裁定）

**不接。** 允许留在 `optimize/` 做「有上限的诊断」，条件是三条：

1. 硬超时必须**按用例时长推导**（上表），不能是裸 10 s 常量；
2. 超时只降级 + 记录，**不改 `Result.status`**（§2.4）；
3. 同一题**最多重试 1 次**，避免诊断把整批总时长拖长。

理由：心跳是为「跑不完的长任务」设计的；诊断档本身有硬上限、且不在正式测量路径上，
再上一层心跳是重复建设。**唯一必须共享的是「超时的语义」：正式状态的 timeout 只能由 harness 产生。**

### 3.2 绝对毫秒 vs 占比（裁定，修正我先前的两处口径）

**两者都给。占比是主、绝对值是辅，且必须写清分母。**

| 要求 | 说明 |
|---|---|
| 必须给占比 | `share = 本行 line_time_ms / 本次已剖析行时间之和`（**分母是「已剖析行时间之和」，不是运行总耗时，也不是 harness 的 `total_ms`**——这正是你提的定义，我认可） |
| 可以给绝对毫秒 | 但**紧邻**标注「插桩后的诊断值，不可与运行耗时比较」 |
| 不得使用的措辞 | 「耗时」「占总时间 X%」「占总运行时间」——一律不许出现，只能写「已剖析行内占比」 |
| `case_ms < 2` | 两者都不给，只给 `hits` |

为什么保留绝对值：顶级 3 行之间用毫秒排序和用占比排序等价，但**毫秒容易被模型读成真实耗时**，
所以用**占比当主口径**压住这个误读；毫秒只在紧跟限定语时保留，方便人看。
（我前面先说过「只准相对量」、后来文档又写「毫秒＋占比」，是我自己的口径不一致，以本节为准。）

## 5. 归属决定：留在 `optimize/`（附理由与合并条件）

**决定：行级计时留在 `optimize/`，不搬进 `eval/`。**

理由：

1. **依赖隔离**：`line_profiler` 是可选第三方依赖。搬进 `eval/` 等于让**所有**测量（时间、内存、复现线）都背上它，
   本机（`C:\Python313`）现在没装，一搬进去全组半数机器直接崩。
2. **职责本来就不重叠**：`eval/hotlines.py` 是 **零依赖的行执行次数**（装不上 line_profiler 时的保底），
   你的是 **带依赖的行耗时**（更准但更重）。两者是「保底/升级」关系，不是「重复实现」。
3. **本期不动 `hotlines` 的公开接口**（这也是你的要求）：所以**不新增** `line_hotspots(mode=...)` 门面。

**但边界要写死**（这是我们说的「一把尺子」落到什么）：

| 归 eval | 归 optimize |
|---|---|
| `PREAMBLE`、`measure_cases`、`split_cases`、五类 status | 子进程、line_profiler 调用、行号/原文校验、行级阈值 |
| 「什么算诊断数字」的字段契约与降级枚举 | 诊断数字的**产生方式** |
| 汇总层（`dual_report` 等）只读 Result，不读诊断 | 诊断只喂提示词，永不进 `Result.time` |

**并进主干的前置条件**（三条都满足才合并）：
1. F2/F3/F4 改完（§1.1、§3、§3.2）；F5 已撤回（`fallback_f2` 合法）；
2. 在**装了 `line_profiler` 的机器**上把 `test_humaneval_40_and_55` 跑绿（本机装不上，三条 real-profiler 测试全 skip，等于没验证）；
3. `can_write_result=False` 的语义保留：完整 F4 在「空间字段定契约」之前不写正式 Result。
