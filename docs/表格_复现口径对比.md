# EffiLearner 复现：旧口径 vs 归一化口径

> 由 `eval/reanalyze_repro.py` 自动生成；数据源 `results/repro/repro_*.json`（组长提交，只读）。
> 只做数值重算，不重新执行代码：结果 JSON 里存了 baseline/final 的 exec_time 与 mem_mbs。

## 一、整体结论

| 项 | 值 |
|---|---|
| 纳入统计的题数 | 328 |
| 时间下降（先求和再算比例） | 21.4% |
| 内存下降 ①旧口径 mem_mbs（全部题） | 30.1% |
| 内存下降 ②旧口径 + 剔除零积分题 | 25.3% |
| **内存下降 ③归一化 + 剔除零积分题（可测口径）** | **9.3%**（n=227） |
| （参考）逐题平均口径：旧 38.1% / 归一化 28.2% | — |
| **零积分题（≈假 100%）** | **101 道（30.8%）** |
| 亚毫秒题（基线 <1ms） | 0 道（0.0%） |
| 时间↓>5% 但内存口径≈0（内存判据看不见的收益） | 3 道 |

**为什么从 ①到③差这么多**：`mem_mbs` 是 RSS-时间积分，近似等于「平均常驻内存 × 执行时间」，所以代码变快本身就会让它下降——①里的降幅大部分是**时间收益的机械副作用**，不是真的更省内存。除以 `exec_time` 得到等效常驻内存后，剩下的才是真正的内存收益；再剔除积分恒为 0 的题（采样点不足），得到的就是敢在答辩里报的 ③。三者满足近似乘法关系：1-(1-③)(1-时间下降) ≈ ①，可直接用数字自检。

> 局限：结果 JSON 只存了**被采纳**的 final，所以「时间变快但被内存判据直接丢弃」的候选无法从已提交数据里观察到。要看到它，需要 `effilearner/effi_repro.py` 额外保存每轮候选代码（已列入 `docs/优化计划.md`）。
