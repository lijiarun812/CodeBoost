## 二、结果（论文口径 vs 新口径）

### 表 1  同一批题、同一份 `final_code`

| 指标 | 论文口径（`mem_mbs` 积分 / 墙钟时间） | 新口径（`proto-2026.11`，E=12 去极值） |
|---|---|---|
| 内存降幅 | **−23.1%**（聚合 MB·s），逐题中位 −3.2% | **不可用**（见 §四-1：峰值只有 1 KB 级，17/19 题 baseline 与 final 完全相同） |
| 时间降幅 | **−21.4%**（聚合），逐题中位 −9.7% | **−14.9%**（逐题均值），中位 −5.0% |
| 成功的题 | 19/20 | 19/20（同一批） |
| 基线噪声 | — | CV 中位 7.9%（4.8%–15.7%），噪声地板 1+2CV ≈ **1.16×** |

几点必须说清楚（否则表格会骗人）：

1. **聚合值远大于逐题中位数**（内存 −23.1% vs 中位 −3.2%）：降幅集中在少数几道题（如 `idx=62 Unique Paths` 单题 −83.3%），
   **19 题里有 9 题完全 0 变化**。所以对外只能说「在这 20 题上，平均降 20% 左右，但一半题目没有收益」，不能说「EffiLearner 平均提升 20%」。
2. **新口径的时间降幅系统性小于论文口径**（−14.9% vs −21.4%；11/19 题新口径更保守）。这符合预期：
   论文口径用墙钟总时间，含着测量框架开销与调度抖动；新口径去极值 + E=12 批次，把噪声压掉之后剩下的才是真信号。
3. **题目的绝对耗时才 0.02–0.23 s/次**，重复数被顶到 1 万–2 万次才凑出 0.25 s 的信号。这批题「太简单」不是感觉，是测量学事实（详见 §四-2）。

## 三、两个阻塞性 bug（这次最值钱的产出）

### bug 1：默认 `--profile on_epoch` 让接受判据永不触发（**严重**）

`effi_repro.py` 里 baseline 与候选代码的剖析设置不对称：

```python
profile = args.profile in ("always", "baseline")   # on_epoch → False：baseline 不剖析
base_m  = measure(base_code, ..., profile_lines=profile)

profile_now = args.profile in ("always", "on_epoch")   # on_epoch → True：候选代码剖析
cand_m  = measure(cand_code, ..., profile_lines=profile_now)
```

于是「候选的 mem_mbs」永远带着 `sys.settrace` 逐行剖析的开销，而 baseline 没有。取证（`docs/截图/07_剖析膨胀.png`，
同一份 `canonical_solution`、2000 次重复）：

```
profile off（干净计时）            mem_mbs=   2.680  time=0.1366s   peak=19.9 MB
profile on（settrace 逐行剖析）    mem_mbs=   7.495  time=0.3786s   peak=19.8 MB
profile off 重复一次               mem_mbs=   3.025  time=0.1583s   peak=19.7 MB
剖析带来的虚高：内存 x2.80  时间 x2.77
```

实跑后果：用默认参数跑的前 6 题，**18 轮优化 18 次「保持」**，没有任何一次采纳
（见 `docs/截图/08_剖析不对称_全部拒绝.png`，原始日志 `results/repro_profile_bug/run_on_epoch.log`，
按仓库约定 `*.log` 不入库，只在本机留档）；换成 `--profile off` 后立刻出现「采纳」。

- 影响：**任何人用默认参数跑，都会得到「模型优化无效」的假结论**。
- 我们的绕行：`--profile off`（判据用干净测量；反馈仍可挂剖析文本，但本批未开）。
- 建议组长改：把「测量」与「剖析」彻底分两条子进程——剖析只用于生成反馈文本，**不参与接受判据**；
  或者至少让 baseline 与候选走同一个 `profile_lines` 取值。

### bug 2：`--send-thinking auto` 的厂商白名单漏了阿里云 MaaS，单题卡 5 分钟

```python
def _host_supports_thinking(api_base):
    return any(k in b for k in ("deepseek", "bigmodel", "dashscope"))
```

我们的 `base_url` 是 `ws-wwmf55kmzjxvyyjg.cn-beijing.maas.aliyuncs.com`，三个关键词都不含 → 不发送
`thinking` 字段 → 网关走 reasoning 模式。实测同一请求：

| 请求形态 | 耗时 | 返回 |
|---|---|---|
| 不带 `thinking` 字段 | 54.1 s / 54.3 s / 51.0 s | **200 但 content 为空** |
| 带 `thinking={"type":"disabled"}` | **5.8 s** | 1167 字符，正常 |

`LLMClient.chat()` 遇到空 content 会「翻倍 token 重试」最多 6 次，于是单次调用可卡 5 分钟以上，
外部看起来像进程死了（我们用 `faulthandler` 抓栈才确认卡在 `ssl.read` → `http.client._read_status`）。

- 我们的绕行：显式 `--send-thinking yes --thinking disabled`。
- 建议组长改：白名单加 `maas.aliyuncs.com`；或在空 content 时**先重试一次去掉 thinking 字段**，而不是直接翻倍预算。

### 附带：网络韧性启动器（不是 bug，是本机环境）

本机走 Clash TUN（接口域名被解析到 `198.18.0.x` 假 IP），长连接偶发「握手成功但不回包」。
`tools/run_effi_resilient.py` 只做两件事：把 socket 超时压到 (10 s 连接 / 90 s 读) + `chat()` 外面套 4 次重试，
**不碰任何测量逻辑**（`measure()` / `new_metrics()` / 判据全部原样调用）。

## 四、还没解决的问题（按优先级）

### 1. 新口径的内存列在 EffiBench 小题目上没有分辨力 🔴

19 题里 **17 题**的 `peak_tracemalloc_mb` 在 baseline 与 final 上**完全相同**，量级只有 **0.0010 MB**（1 KB）；
`peak_rss_mb` 两边都是 20.6 MB 上下（差值 <0.1 MB，被解释器基线淹没）。也就是说：

> 这批题目的内存降幅，新口径**测不出来**，论文口径能测出 −23.1% 但它用的是「RSS 对时间积分」这种近似。

这不是算错，是**题目太小**：一次调用的分配峰值只有 KB 级，任何固定开销都盖过它。
三条出路（需要组长/我来定）：
(a) 只统计「落在被测函数内部」的分配（tracemalloc 快照差分 + 过滤）；
(b) 换更大的题（`baseline_ms ≥ 20 ms`、headroom ≥ 1.5 的冻结题库，B 线正在做）；
(c) 内存判据暂时只在「大题目子集」上报告，并在表里注明 subsample。

### 2. 失败率与「树/链表题」缺失 🟠

本批 20 题只失败 1 题（`idx=49 Group Anagrams`，`AssertionError`），比之前 100 题批次的 13–21% 低，
但那是因为这批题恰好少树/链表。之前在 100 题批次上，`ListNode` / `TreeNode` / `build_tree` 未注入导致
`NameError`，属于同一类问题。**注入修复仍是必需项**，否则 %Correct 会随题目难度随机波动。

### 3. 模型矩阵没有新口径数字 🟠

旧口径有 4 个模型（deepseek-flash / qwen3-coder-flash / glm-4.6 / deepseek-v4-pro，各 ~80–87 题成功），
新口径只有本次这 1 个模型 20 题。老师的第 2 条要求（多模型）目前**只有单列证据**。

### 4. 优化线（B/C/D）仍是 0 进度 🟠

`datasets` 冻结题库（B）、热点区域反馈（C）、`optimize/` 的 Ours v2（D）都还没开始，
评分表里「优化 20 分」目前没有任何可交付物。
