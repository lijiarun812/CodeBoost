## 二、结果（TMU 口径 vs 新口径）

> **口径更正（2026-11-27 晚）**：本文原先写的「内存降 23.1%」是**错误的叫法**。那一列是
> `mem_mbs = ∫RSS dt ≈ 峰值 × 耗时`，即论文 Table 1 的 **TMU**（内存-时间积分）的一个**近似实现**，
> 本质是**耗时代理**，不是空间指标。论文还有另一列 **MU（峰值内存，MB）**，我们此前**从未测过**。
> 下面所有「内存」字样都已改成「TMU」。完整对照见 [`表格_双口径_effilearner.md`](表格_双口径_effilearner.md)。

### 表 1  同一批题、同一份 `final_code`

| 指标 | TMU（`mem_mbs` 积分，本实现近似） | 新口径（`proto-2026.11`，E=12 去极值） |
|---|---|---|
| TMU 降幅 | **−23.1%**（聚合 MB·s），逐题中位 −3.2% | — |
| 时间降幅 | **−21.4%**（聚合），逐题中位 −9.7% | **−14.9%**（逐题均值），中位 −5.0% |
| MU（峰值内存）降幅 | — | **≈ 0%**（19/19 题 peak_rss 全部贴在 20.5 MB 空载基线上，无可分辨信号） |
| 成功的题 | 19/20 | 19/20（同一批） |
| 基线噪声 | — | CV 中位 7.9%（4.8%–15.7%），噪声地板 1+2CV ≈ **1.16×** |

几点必须说清楚（否则表格会骗人）：

1. **TMU 的降幅就是耗时降幅的投影**，有硬证据：逐题配对相关
   `r(TMU 降幅, 时间降幅) = 0.936`（本批）/ `0.967`（第二批），而 `r(MU−基线降幅, 时间降幅) = 0.378 / −0.198`。
   同一个量不可能既等于时间又独立于时间——**所以 TMU 这一列不能用来讲「省了多少内存」。**
2. **聚合值远大于逐题中位数**（TMU −23.1% vs 中位 −3.2%）：降幅集中在少数几道题（如 `idx=62 Unique Paths` 单题 −83.3%），
   **19 题里有 9 题完全 0 变化**。所以对外只能说「在这 20 题上，平均降 20% 左右，但一半题目没有收益」，不能说「平均提升 20%」。
3. **新口径的时间降幅系统性小于 TMU 口径**（−14.9% vs −21.4%；11/19 题更保守）。这符合预期：
   TMU 口径用墙钟总时间，含测量框架开销与调度抖动；新口径去极值 + E=12 批次，把噪声压掉之后剩下的才是真信号。
4. **MU 这一列在这批题上是 0 信号**（不是我们没测，是题目太小）：空载 RSS 20.5 MB，
   全部题的 `peak_rss` 也在 20–21 MB，扣掉基线后无一题达到 5 MB 的可分辨门槛。
   这与「TMU 讲不出空间」是**两件独立的事**，两条都指向同一个结论：**要谈空间，必须有更大的输入**。
5. **题目的绝对耗时才 0.02–0.23 s/次**，重复数被顶到 1 万–2 万次才凑出 0.25 s 的信号。这批题「太简单」不是感觉，是测量学事实（详见 §四-2）。

## 三、两个阻塞性 bug（这次最值钱的产出）

### bug 1：默认 `--profile on_epoch` 让接受判据永不触发（**严重**）

`effi_repro.py` 里 baseline 与候选代码的剖析设置不对称：

```python
profile = args.profile in ("always", "baseline")   # on_epoch → False：baseline 不剖析
base_m  = measure(base_code, ..., profile_lines=profile)

profile_now = args.profile in ("always", "on_epoch")   # on_epoch → True：候选代码剖析
cand_m  = measure(cand_code, ..., profile_lines=profile_now)
```

于是「候选的 mem_mbs」永远带着 `sys.settrace` 逐行剖析的开销，而 baseline 没有。取证（`docs/截图/07_剖析膨胀.png`，
同一份 `canonical_solution`、2000 次重复）：

```
profile off（干净计时）            mem_mbs=   2.680  time=0.1366s   peak=19.9 MB
profile on（settrace 逐行剖析）    mem_mbs=   7.495  time=0.3786s   peak=19.8 MB
profile off 重复一次               mem_mbs=   3.025  time=0.1583s   peak=19.7 MB
剖析带来的虚高：内存 x2.80  时间 x2.77
```

实跑后果：用默认参数跑的前 6 题，**18 轮优化 18 次「保持」**，没有任何一次采纳
（见 `docs/截图/08_剖析不对称_全部拒绝.png`，原始日志 `results/repro_profile_bug/run_on_epoch.log`，
按仓库约定 `*.log` 不入库，只在本机留档）；换成 `--profile off` 后立刻出现「采纳」。

- 影响：**任何人用默认参数跑，都会得到「模型优化无效」的假结论**。
- 我们的绕行：`--profile off`（判据用干净测量；反馈仍可挂剖析文本，但本批未开）。
- 建议组长改：把「测量」与「剖析」彻底分两条子进程——剖析只用于生成反馈文本，**不参与接受判据**；
  或者至少让 baseline 与候选走同一个 `profile_lines` 取值。

### bug 2：`--send-thinking auto` 的厂商白名单漏了阿里云 MaaS，单题卡 5 分钟

```python
def _host_supports_thinking(api_base):
    return any(k in b for k in ("deepseek", "bigmodel", "dashscope"))
```

我们的 `base_url` 是 `ws-wwmf55kmzjxvyyjg.cn-beijing.maas.aliyuncs.com`，三个关键词都不含 → 不发送
`thinking` 字段 → 网关走 reasoning 模式。实测同一请求：

| 请求形态 | 耗时 | 返回 |
|---|---|---|
| 不带 `thinking` 字段 | 54.1 s / 54.3 s / 51.0 s | **200 但 content 为空** |
| 带 `thinking={"type":"disabled"}` | **5.8 s** | 1167 字符，正常 |

`LLMClient.chat()` 遇到空 content 会「翻倍 token 重试」最多 6 次，于是单次调用可卡 5 分钟以上，
外部看起来像进程死了（我们用 `faulthandler` 抓栈才确认卡在 `ssl.read` → `http.client._read_status`）。

- 我们的绕行：显式 `--send-thinking yes --thinking disabled`。
- 建议组长改：白名单加 `maas.aliyuncs.com`；或在空 content 时**先重试一次去掉 thinking 字段**，而不是直接翻倍预算。

### 附带：网络韧性启动器（不是 bug，是本机环境）

本机走 Clash TUN（接口域名被解析到 `198.18.0.x` 假 IP），长连接偶发「握手成功但不回包」。
`tools/run_effi_resilient.py` 只做两件事：把 socket 超时压到 (10 s 连接 / 90 s 读) + `chat()` 外面套 4 次重试，
**不碰任何测量逻辑**（`measure()` / `new_metrics()` / 判据全部原样调用）。

## 四、还没解决的问题（按优先级）

### 1. 空间列在 EffiBench 小题目上没有分辨力（原写「全不可用」，已修正）🔴

19 题里 **17 题**的 `peak_tracemalloc_mb` 在 baseline 与 final 上**完全相同**，量级只有 **0.0010 MB**（1 KB）；
`peak_rss_mb` 两边都是 20.5 MB 上下（空载基线就是 20.5 MB，差值 <0.1 MB）。也就是说：

> 这批题目的空间降幅，两个新口径（tracemalloc / peak_rss）**都测不出来**。
> TMU 能「测出」−23.1%，但那只是耗时降幅的投影（`r = 0.936`），不是空间收益。

**但要修正我此前那句「全不可用」**——补测 24 题（`results/_peak_sample/sample.json`）后分布是这样的：

| tracemalloc 峰值 | 题数 |
|---|---|
| 中位 | 0.0017 MB |
| 最大 | **1.3675 MB**（`idx=22 Generate Parentheses`） |
| ≥ 0.1 MB | **5 / 22（23%）** |
| ≥ 0.01 MB | 8 / 22 |

`peak_rss` 也有真实差异：`idx=35` 到 **63.2 MB**、`idx=22` **29.0 MB**、`idx=254` **25.0 MB**。
所以正确说法是「**约 1/4 的题有可分辨的空间信号**」，不是「全不可用」。
而本次两批 40 题恰好全落在没信号的那 3/4 里（同一批题、同一个模型），这也解释了为什么表 1b 的 MU 全是 0。

四条出路：
(a) 只统计「落在被测函数内部」的分配（tracemalloc 快照差分 + 过滤）；
(b) **按空间信号筛题**：`peak_tm ≥ 0.05 MB`（按 23% 通过率，1000 题约剩 230 题，够 B 的 120–200）；
(c) **输入规模升档**（n: 1e3→1e4→1e5，只进 `diagnostic_only`）——这是 `eval/inputs.py` 的能力，归我；
(d) 空间判据暂时只在「有信号子集」上报告，并在表里注明 subsample。

### 2. 失败原因已经换了一类：从「测量缺件」变成「模型写错」🟠→✅（部分）

本批 20 题（`start=0`）只失败 1 题（`idx=49 Group Anagrams`，`AssertionError`）。但更要紧的是**修复后的验证**：

| 批次 | 题目区间 | 成功 | 失败原因 | `NameError: build_tree` |
|---|---|---|---|---|
| 第一批 `repro_dual` | 前 20 题（`start=0`） | 19/20 | `AssertionError` ×1 | 该区间未出现 |
| 第二批 `repro_dual_postfix` | 后 20 题（`start=100`，含大量树/链表题） | **17/20** | `AssertionError` ×3 | **0 次**（`idx=250` 已能正常跑） |

组长在 `f4a1d97` / `4fccdbd` 里注入 tree/list helper 之后，同一批树题**不再缺件**，
剩下的 3 次失败全是 `AssertionError`——即**模型生成的初始代码本身过不了测试**，属于模型能力，
不是测量管线的问题。这两类失败必须分开报（`%Correct` 的分子分母都由它决定），
否则「失败率 15%」会被误读成「复现不完整」。

`docs/截图/09_修复后_汇总.png`、`10_修复后_树题通过.png`。

### 2b. 第二批（含树题）的降幅数字

同一套配置（`--profile off`，paper 判据）：

| 批次 | 成功 | 论文口径 内存 / 时间 | 新口径 时间 | 新口径 内存 |
|---|---|---|---|---|
| 前 20 题 | 19/20 | −23.1% / −21.4% | −14.9% | 不可用 |
| 后 20 题（树题多） | 17/20 | −18.8% / −16.0% | −11.6% | 不可用（3/15 题非零） |

两批合起来 34 题、新口径基线 CV 中位 **6.6%**（2.9%–15.7%），噪声地板 **1.13×**。
方向一致：**新口径永远比论文口径更保守**，这正是我们要在报告里说清楚的那件事。
