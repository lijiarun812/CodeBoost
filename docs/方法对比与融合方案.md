# PerfCodeGen × EffiLearner：定位、对比、融合与其他优化方向

> 一句话：**EffiBench 是“考场”，PerfCodeGen 和 EffiLearner 是两种“提分方法”**——
> 一个靠「最慢的那个测试用例」告诉模型时间花在哪，一个靠「行级剖析」告诉模型具体哪一行贵。
> 我们组的实验先后各用了其中一种，但两种都只用到了一半（下面第 3 节有证据）。
> 本文档要回答的四件事：组长用的到底是哪套、两套差在哪、怎么融合、还能怎么优化。

---

## 一、三篇论文的定位

| 论文 | 会议 | 角色 | 核心贡献 | 能不能直接借来用 |
|---|---|---|---|---|
| **EffiBench** | NeurIPS 2024 Datasets & Benchmarks | **基准/数据集**（不是框架） | 1000 道 LeetCode 效率关键题（每题配 canonical solution）+ 效率指标；评测 42 个 LLM | 只能当评测集：我们的 100 题就是取它的前 100 道 |
| **PerfCodeGen** | FORGE 2025 @ ICSE | **优化框架** | 两阶段自精炼：①失败用例反馈修正确性 ②**最慢测试用例 + 其耗时**修效率；20 采样 + Best@k；%Opt / Speedup 指标 | 提示词模板可直接用（已 vendor 进 `perfcodegen/upstream/`） |
| **EffiLearner** | NeurIPS 2024 | **优化框架** | 把 **line_profiler / memory_profiler 的行级剖析**拼进提示，多轮自我迭代；ET / MU / TMU 指标 | 提示词结构在 `CodeBoost/prompts.py`（SOAP 档） |

**证据**（EffiBench 摘要原话的量级）：GPT-4 生成的代码平均是标准解的 **3.12 倍**耗时，极端情况 **13.89 倍**耗时、
**43.92 倍**总内存。这就是“功能正确但效率低下”的量化出处，第 2 页 motivating example 可以直接引。

## 二、两个框架的八维对比

| 维度 | PerfCodeGen | EffiLearner |
|---|---|---|
| **优化目标** | 主要是**时间**（speedup / %Opt）；内存不在主指标 | **时间 + 内存**（ET / MU / TMU / NMU / NTMU） |
| **反馈信号** | 「最慢的那个测试用例」+ 它的耗时（一个点，信息量很小） | 「每行的耗时/内存热点」（一张表，信息量大但很长） |
| **反馈形态** | 自然语言 + 一个测试用例源码 | 自然语言 + profiler 原始输出（`prompts.py` 里 `line_profiler_results`、`memory_report`） |
| **阶段设计** | **两阶段显式分离**：先保证正确性，再优化性能；优化后跑不过测试就回退 | **无独立正确性阶段**：假定输入已是“通过全部用例的代码”（只统计通过的题） |
| **迭代轮数** | 论文主实验性能阶段基本 1 轮（模板支持多轮负反馈） | **多轮**（我们复现设 3 轮）；作者观察到多轮后收益递减 |
| **采样与择优** | **20 采样 + Best@k**（k=1,5,8,10,20） | 单样本逐题迭代（不做采样择优） |
| **采纳判据** | 更优即采纳，失败回退 | 开销更低才采纳（官方实现偏内存） |
| **指标口径** | %Correct / %Opt（比 GT 快 10%）/ Speedup / Best@k | ET / MU / TMU / NMU / NTMU（相对 canonical solution） |
| **单题成本** | 低（1 次优化调用 + 测试执行） | 高（每轮都要跑 profiler，行级 profiler 很慢） |
| **典型失效模式** | 反馈信息太少 → 模型“猜”着改，改错地方 | 反馈信息太多 → 信息过载 / 过度优化改坏正确性 |

> 一句话记住：**PerfCodeGen = 点位反馈（便宜、粗糙）；EffiLearner = 剖面反馈（贵、精确）**。

## 三、四条相通之处（这是“能融合”的前提）

1. **都是 training-free 的自精炼闭环**：生成 → 执行 → 反馈 → 再生成，没有梯度更新、不改模型参数。
   所以两者的循环可以拼成一个循环，不需要重训。
2. **都要求“先有正确代码”**：PerfCodeGen 用显式正确性阶段保证，EffiLearner 用“只统计能通过用例的题”绕过。
   前者更严谨，后者更省成本 —— 融合时应该取前者。
3. **反馈都来自执行侧证据**（运行时行为），不是静态分析；因此都需要可信的沙盒与测量。
   **这正好是我们组的强项**（`eval/measure.py` 的重复放大 + MAD + Pareto 判据）。
4. **都是“更优才保留”的爬山**，没有全局搜索。两条路线都受“初稿质量”和“局部最优”限制，
   而这正是 PerfCodeGen 的 Best@k 能补的位置。

### 3.1 一个必须讲清的事实：组长那轮只跑到 EffiLearner 的第 4 档

EffiLearner 官方提示词有 5 个档位（`CodeBoost/prompts.py` 可证）：

| 档位 | 反馈内容 | 组长跑过吗 |
|---|---|---|
| SOAP（完整） | 3 个汇总数字 + **行级时间剖析** + **内存剖析报告** | ❌ |
| 仅行级时间 | 3 个数字 + line_profiler 结果 | ❌ |
| 仅内存剖析 | 3 个数字 + memory_profiler 结果 | ❌ |
| **result-aware** | 只有 3 个汇总数字（mem MB*s / time / peak） | ✅ 现在这 100 题就是这个 |
| unsupervised | 无 overhead，只说“优化” | ❌ |

组长的 `effilearner/effi_repro.py` 的 `overhead_text()` 只输出那 3 个数字 —— 也就是说
**「行级剖析」这个 EffiLearner 的核心信号从来没接上**。这解释了为什么我们的下降率比论文低一个量级：
我们复现的是最弱的那个档。这句话建议直接在汇报里说，比硬解释“我们不如论文”强得多。

## 四、融合方案

### 4.1 融合架构（一句话版）

```
题目 ──► ① Base 采样 k 份（PerfCodeGen 的 Best@k）
      ──► ② 正确性精炼：失败用例 + 报错 回灌（PerfCodeGen §2.1）
      ──► ③ 阶段门控：只让"通过全部用例"的版本进入优化
      ──► ④ 证据包分级：最慢用例 → +per-case 表 → +行级热点（PerfCodeGen × EffiLearner）
      ──► ⑤ 预算化多轮：收益 <5% 或连续无收益即停（EffiLearner 的迭代 + 我们的早停）
      ──► ⑥ Pareto 择优：时间变快且内存不劣化才采纳；对 k 份取最好
      ──► ⑦ 指标：%Correct / %Opt / Speedup / Best@k（论文口径）
```

### 4.2 五个融合点（按性价比排序，都给了可跑的实验设计）

| # | 融合点 | 动机（来自哪个观察） | 做法 | 实验设计 | 成本 | 预期 |
|---|---|---|---|---|---|---|
| 1 | **证据包分级（granularity ladder）** | 中期 Ours 更差 + EffiLearner 的多轮递减 → 信息过载 | 同一次优化按 `--evidence slowest/table/hotlines/all` 升档 | 20 题 × 4 档 × 单轮，比较 %Opt / Speedup / 反馈长度 | 低（1 次调用/题） | “加信息不一定更好”，能找到拐点 |
| 2 | **两阶段顺序 + 回退** | 13–21% 的题在优化后改坏 | 正确性阶段先锁定，性能阶段失败回退（已实现） | 对照：先优化后修错 vs 先修错后优化 | 中 | %Correct 明显提升，%Opt 略降 |
| 3 | **Best@k × 迭代** | 爬山易陷局部最优 | k 份初稿各迭代 1 轮，再按 Pareto 择优 | k=1/5/10 × 1 轮 vs k=1 × 3 轮（同调用预算） | 中高 | 同预算下 Best@5 优于单稿多轮 |
| 4 | **预算化早停** | EffiLearner 观察到多轮收益递减 | `--min-gain 0.05 --patience 1` 已实现 | 3 轮 vs 早停：收益/调用数比 | 低 | 省 30–50% 调用，收益几乎不降 |
| 5 | **热点 RAG / few-shot** | `time_in_context_learning` 模板证明 few-shot 有效 | 按 EffiBench 题目标签聚类，检索历史成功改写做示例 | 无示例 / 随机示例 / 同类示例 | 中 | 同类示例组收益最高（可作“课程 RAG”联系点） |

### 4.3 代码里怎么落地（现在就能跑）

| 命令 | 对应档位 | 用途 |
|---|---|---|
| `--time-strategy none` | 不优化 | 只测 base（上界/下界对照） |
| `--time-strategy simple` | 盲优化 | 对照组：只给“优化一下” |
| `--time-strategy feedback` | PerfCodeGen 原档 | 最慢用例 + 耗时 |
| `--time-strategy effi3num` | EffiLearner 的 result-aware 档 | **和组长那轮同档**，用于同题同模型对照 |
| `--time-strategy fusion` | 融合档 | 最慢用例 + per-case 表 + 行级热点 + 复杂度引导 |
| `--evidence slowest/table/hotlines/all` | 证据包旋钮 | 单独做“信息量”消融 |
| `--min-gain 0.05 --patience 1` | 早停 | 预算控制 |

每轮都会把 `evidence`（档位）、`evidence_chars`（反馈长度）、`evidence_pack`（实际喂进去的前 800 字）
写进逐题 JSON —— 这样“反馈长度 vs 收益”这条曲线可以直接画出来。

## 五、其他可优化的方向（不一定都做，挑 2 条做深就够）

| # | 方向 | 动机 | 做法 | 成本 | 风险 |
|---|---|---|---|---|---|
| 1 | **输入规模放大** | 亚毫秒题噪声 > 收益（中期 6/8 题踩坑） | 用更大的输入重跑最慢用例，或按题构造规模递增的用例 | 低 | 放大后语义可能变（越界、超时） |
| 2 | **剖析结果 LLM 摘要** | 行级原始输出太长 → 信息过载 | 先用一次便宜调用把 profiler 输出压成 3 条要点，再喂优化 | 中（多 1 次调用） | 摘要有信息损失 |
| 3 | **复杂度引导两轮** | 模型常“改错地方” | 模板 `time_time_complexity_reduction` 已现成：先估复杂度，再改 | 低（多 1 轮） | 复杂度估错会带偏 |
| 4 | **多智能体 reviewer** | 优化后改坏正确性 | 模板 `time_multiple_agents_with_reviewer` 现成：优化 → 评审 → 再改 | 高（×2~3 调用） | 成本高、收益不稳定 |
| 5 | **LoRA 微调“优化直觉”** | 课程实验 5 有微调能力 | 用成功改写对（原始→优化）构造 SFT 数据，微调小模型 | 高（要 GPU） | 数据少易过拟合，答辩易被问“和提示工程区别” |
| 6 | **静态启发式前置** | 有些优化不需要模型（循环外提、去重复计算） | 写几条 AST 规则做 cheap baseline，再让模型接手 | 低 | 覆盖面窄，但可作为“零成本 baseline”对照 |

**优先级建议**：先做第 1、4 节里的融合点 1（证据包分级）+ 点 4（早停）——两者都只需改命令行，
一次跑完就能出“信息量-收益”曲线；第 5 条 LoRA 留作“展望”，不要真做（时间不够且风险高）。

## 六、汇报怎么讲（三段话，对应 PPT 第 3 / 8 / 9 页）

**第 3 页（技术路线）**：
> “我们把两条路线放在同一个坐标系里：PerfCodeGen 是**点位反馈**（最慢用例，便宜但粗糙），
> EffiLearner 是**剖面反馈**（行级剖析，精确但贵且容易信息过载）。它们其实是同一条自精炼闭环上的
> 两个信息量档位，所以我们把反馈粒度做成了一个可调的旋钮。”

**第 8 页（优化动机）**：
> “复现时我们发现两件事：一是我们只跑到 EffiLearner 的 result-aware 档（只给 3 个数字，行级没接），
> 所以下降率天然低于论文；二是中期细粒度反馈反而更差，我们怀疑是信息过载而不是方法无效。
> 于是我们把反馈做成 5 档，用同一批题、同一模型、同一测量口径做消融。”

**第 9 页（优化结果）**：
> “我们给出了‘反馈长度 vs 收益’的曲线：从 simple 到 feedback 收益上升，再到 fusion（表 + 热点行）
> 收益不再上升甚至回落；配合早停，调用量下降 X% 而收益基本不变。这支持‘信息过载’假设，
> 也给出了工程上的推荐档位。”

## 七、事实与出处（被追问时直接翻）

| 事实 | 出处 |
|---|---|
| EffiBench：1000 题 / 42 模型 / GPT-4 平均 3.12× | `doc/EffiBench.pdf` 摘要（p.1） |
| PerfCodeGen：最慢用例反馈、20 采样、Best@k、~47%/~56% | `doc/PerfCodeGen.pdf` 摘要（p.1）+ 官方 README |
| PerfCodeGen 的提示词档位（含 few-shot / CoT / 复杂度 / 多智能体） | `perfcodegen/upstream/templates_chat.json` 的 13 个键 |

| 组长那轮只给 3 个数字 | `effilearner/effi_repro.py` 的 `overhead_text()` |
| 组长中期用的是 PerfCodeGen 风格 | 中期 docx 正文 + `pcg_verify` 轨迹（阶段1 基线复核 → 阶段2 剖析/反馈） |
